## 2. 기술 선택

- 프런트엔드: 기존 HTML/CSS와 바닐라 JavaScript의 ES modules를 사용한다. 현재 기능 규모에서는 React·Next.js·TypeScript 도입을 필수로 삼을 이유가 적다.
- 데이터 수집·배포 준비: Node.js LTS와 기본 `fetch`, 파일 처리, `node:test`를 중심으로 구성한다. 실제 구현 시 런타임 버전을 고정한다.
- jQuery: 공통 데이터 로딩·이벤트·DOM 작업을 단계적으로 표준 API로 교체한다. 디자인을 유지하면서 의존성을 줄인다.
- 호스팅: GitHub Pages 유지. 로또 공식 데이터는 Actions에서 수집하고 방문자는 같은 사이트의 검증된 JSON을 읽는다.
- 댓글: giscus + GitHub Discussions. 별도 회원·댓글 DB·프런트엔드 GitHub 토큰은 필요 없다.
- 빌드: 공개 설정 주입과 배포 파일 선별을 위한 작은 Node.js 스크립트를 둔다. 큰 번들러는 초기 필수 범위에 넣지 않는다.

권장 데이터 흐름:

```text
동행복권 공식 조회 응답
  → Node.js 수집기: 응답 변환·누락 회차 보충·검증
  → 당첨 기록 + 기록에서 계산한 빈도 + 갱신 메타데이터
  → GitHub Actions: 검증·변경 저장·정적 파일 준비·Pages 배포
  → 브라우저: 같은 출처의 JSON으로 홈·통계·번호 생성 표시
```

## 3. 구현 순서와 완료 기준

### 1단계: Node.js 수집기와 데이터 복구

1. `scripts/update-lotto.mjs`와 공식 응답 변환 모듈을 만든다.
2. 최신 발표 회차는 `https://www.dhlottery.co.kr/lt645/selectPstLt645Info.do`의 실제 응답에서 읽는다.
3. 과거 회차는 공식 결과 화면에서 사용하는 `https://www.dhlottery.co.kr/lt645/selectPstLt645InfoNew.do`를 사용한다.
   - 조사 시 `srchDir=center&srchLtEpsd=1203` 요청이 1203회를 포함한 여러 회차를 반환했다.
   - 배열 순서나 한 요청에 정확히 한 회차가 온다는 가정을 하지 않는다. 회차별로 식별·중복 제거·정렬한다.
   - 기존 1203회와 새 응답의 번호·날짜·금액이 일치하는 것도 확인했다.
4. 신규 필드 `ltEpsd`, `ltRflYmd`, `tm1WnNo`~`tm6WnNo`, `bnsWnNo`, `rnk1WnAmt` 등을 기존 화면 데이터 형식으로 변환한다. 1차에서는 기존 당첨 기록 필드명을 유지해 변경 범위를 줄인다.
5. 기존 기록을 보존하고 누락 회차만 보충한다. 최근 저장 회차는 겹쳐 조회해 공식 정정과 충돌을 감지한다. 번호·날짜 충돌은 자동 덮어쓰기하지 않고 실패로 보고한다.
6. 빈도 파일은 당첨 기록 전체에서 다시 계산한다. 본번호 6개만 집계하고 보너스는 제외한다. JSON 숫자형을 명확히 한다.
7. HTTP 상태뿐 아니라 Content-Type·JSON 구조·날짜·정수 범위·회차 중복/누락·본번호와 보너스 중복·금액 필드를 검증한다. 과거 1등 당첨자 0명 등 실제 유효한 기록을 허용한다.
8. 타임아웃·제한된 재시도·요청 간격을 둔다. HTML 응답·접근 차단·불완전 데이터는 정상적인 갱신 완료로 처리하지 않는다.
9. 임시 파일에서 전체 검증을 통과한 데이터 묶음만 반영한다. 실패하면 마지막 정상 데이터를 보존한다. `--check`로 저장 없이 검증할 수 있게 한다.
10. 데이터 저장 위치를 `data/`로 옮기고 Java 소스·클래스·JAR를 제거한다. 이전 기록은 Git 이력으로 보존된다.

완료 기준: 공식 최신 발표 회차까지 빈틈 없이 존재하고, 빈도 합계가 `회차 수 × 6`이며, 같은 입력으로 재실행하면 데이터 차이가 없다. 네트워크 실패 시 기존 파일이 유지된다.

### 2단계: 자동 갱신과 Pages 배포

1. 수동 실행과 예약 실행을 지원하는 갱신 워크플로를 추가한다.
2. 권장 실행 시각은 한국 시간 토요일 21:17·22:17, 일요일 07:17이다. 정시를 피해 실행하고 발표 지연을 재확인한다. 정확한 시각 실행은 보장하지 않는다.
3. 최신 번호·날짜는 공식 응답을 기준으로 정한다. 추첨일로 다음 회차 번호를 계산해 당첨 데이터로 표시하지 않는다.
4. 정상적인 변경이 있을 때 데이터만 커밋하고, 같은 실행의 후속 작업으로 Pages에 배포한다. 변경이 없는 경우 불필요한 커밋을 만들지 않는다.
5. `GITHUB_TOKEN`으로 만든 커밋이 별도의 push 워크플로나 Pages 빌드를 다시 실행할 것이라고 가정하지 않는다. 수집→검증→저장→배포 연결을 명시한다.
6. 일반 코드 push도 동일한 검증·배포 로직을 재사용한다. PR에서는 검사만 수행한다.
7. 갱신 실행과 코드 배포의 동시 실행을 제어하고, 최신 코드 및 갱신 데이터가 함께 배포되도록 한다. 브랜치 보호가 직접 데이터 커밋을 막으면 데이터 PR 경로로 조정한다.
8. 데이터 저장 작업에만 `contents: write`, 배포 작업에 필요한 Pages/OIDC 권한만 부여한다. 개인 액세스 토큰을 기본 구성으로 요구하지 않는다.
9. Actions 실패 상태·실행 요약·마지막 정상 갱신 정보를 남긴다. 실패 통지 설정과 공개 저장소 예약 작업의 60일 비활동 자동 중지 시 복구 방법을 문서화한다.

완료 기준: 수동 갱신 실행 한 번으로 검증된 최신 JSON이 실제 배포까지 이어지고, 실패한 수집 결과는 배포되지 않는다. GitHub-hosted runner에서도 공식 조회가 되는지 별도로 확인한다.

### 3단계: 화면·날짜·링크 복구

1. `js/data.js`에 공통 데이터 로더를 두고 모든 화면이 상대 경로로 같은 데이터 묶음을 읽게 한다.
2. 홈에 회차, 추첨일, 본번호 6개와 보너스, 1인당 1등 금액·당첨자 수를 명확히 표시한다. 현재 `수령 금액 기준` 문구는 추첨일로 바로잡는다.
3. 데이터 갱신 시각과 추첨일을 구분한다. 오래된 데이터는 기준 회차와 상태를 표시하며 최신이라는 인상을 주지 않게 한다.
4. 홈에서 랜덤 번호를 생성하면 해당 번호가 최신 당첨번호와 혼동되지 않도록 생성 상태·당첨번호 복귀 동선을 제공한다.
5. 로딩·실패·데이터 없음 상태를 만들고, 데이터가 필요한 버튼은 준비될 때 활성화한다. 통계가 실패해도 일반 랜덤 생성은 사용할 수 있게 한다.
6. 공식 링크를 한 설정으로 관리한다. 홈페이지 `/`, 소개 `/lt645/intro`, 결과 `/lt645/result`, 판매점 `/prchsplcsrch/home`이 현재 유효한 경로임을 확인했다.
7. 구매는 공식 사이트의 로그인·기기·운영 조건을 거치는 기능이다. 조사한 공식 구매 코드도 로그인과 서버 설정에 따라 이동 경로를 결정한다. 초기 기본값은 공개 구매 안내/공식 홈페이지의 구매 진입 동선으로 연결하고 버튼 이름도 실제 목적지에 맞춘다. 검증되지 않은 세션 의존 구매 URL을 하드코딩하지 않는다.
8. `navigator.platform` 기반 모바일 차단과 옛 모바일 URL 분기를 제거한다. 구매 가능 시간 등 변동 가능한 내용은 공식 안내로 연결한다.
9. 공통 메뉴·링크·제목 처리 중복을 줄인다. 기존 HTML URL과 GitHub Pages의 `/lottoworld/` 하위 경로를 보존한다.

완료 기준: 로컬·Pages 모두 같은 데이터가 표시되고, 구매·소개·홈페이지·통계 링크가 오류 페이지로 이동하지 않는다. 로딩 실패를 정상 번호나 빈 화면으로 오해하지 않는다.

### 4단계: GitHub 댓글

1. 저장소 Discussions를 활성화하고 giscus 앱을 해당 저장소에 연결한다.
2. 댓글용 카테고리를 정한다. giscus 권장 방식인 Announcements 유형을 우선 검토한다.
3. 실제 repository/category ID를 조회한 뒤 설정한다. ID는 공개 설정이며 임의 값으로 채우지 않는다.
4. `comment.html`의 LiveRe 코드를 giscus로 교체한다. 한국어·반응·지연 로딩을 적용한다.
5. 한 개의 댓글 화면이므로 URL 변경에 덜 민감한 고정 식별자로 Discussion을 매핑하고 엄격한 일치를 사용한다.
6. 위젯을 불러오지 못하면 GitHub Discussions 직접 방문 링크와 안내를 표시한다.
7. GitHub에 댓글이 공개 저장됨을 안내한다. 기존 LiveRe 댓글 이전은 내보내기 가능 여부를 확인한 후 별도로 결정한다.

완료 기준: 비로그인 사용자는 댓글을 읽고, GitHub로 로그인한 사용자는 댓글·답글·반응을 사용할 수 있다. 저장소 관리자가 Discussions에서 관리할 수 있다. 실제 댓글 등록 검증은 테스트용 글 게시에 대한 명시적 요청이 있을 때 진행한다.

### 5단계: 카카오 지도 설정과 오류 처리

브라우저가 사용하는 JavaScript SDK 키는 개발자 도구와 네트워크 요청에서 볼 수 있다. `.env`나 Actions Secrets에서 주입하더라도 배포된 키가 비밀이 되는 것은 아니다.

권장안은 기존 지도를 유지하면서 다음을 적용하는 것이다.

1. HTML 하드코딩을 제거한다. 로컬 설정은 Git에서 제외하고 예제 설정만 커밋한다. 배포 시 환경 설정에서 공개 SDK 설정을 생성한다.
2. 카카오 개발자 콘솔에서 실제 서비스 도메인과 필요한 localhost만 허용한다. GitHub Pages 도메인 제한은 저장소 경로 단위의 격리를 보장하는 것으로 설명하지 않는다.
3. 카카오맵 사용 활성화·사용량·쿼터 상태를 확인한다. 현재 키 재발급 필요 여부는 소유자와 사용 현황을 확인한 뒤 결정한다. 공개 JavaScript 키라는 이유만으로 Git 이력 전체를 재작성하지 않는다.
4. 지도 버튼을 누른 후 SDK·위치 정보를 준비한다. 위치 거부·시간 초과·키 누락·SDK 로딩 실패를 처리한다.
5. 위치가 없으면 기본 위치 또는 사용자가 선택한 지도 중심을 사용하고 그 기준을 표시한다. 외부 공식 판매점 검색과 카카오맵 검색 링크를 대체 동선으로 제공한다.
6. 지도 표시 후 크기를 다시 계산하고 재검색 전 기존 마커를 정리한다. 검색 반경을 설정 하나로 통일한다.
7. 장소 이름을 HTML 문자열에 직접 삽입하지 않고 텍스트로 렌더링한다. 위치 좌표는 저장소·운영 로그에 기록하지 않는다.

키가 방문자에게도 전혀 노출되지 않아야 한다면 별도 선택이 필요하다. 가장 단순한 대안은 임베드 지도를 제거하고 공식 판매점/카카오맵 검색 링크를 사용하는 것이다. 서버 프록시는 REST API 비밀키를 보호할 수 있지만, 현재 JavaScript 지도 SDK 키까지 숨기는 해결책은 아니다.

완료 기준: 키·위치가 없어도 홈과 번호 기능이 정상 작동하고, 지도에는 잘못된 좌표가 전달되지 않는다. 설정 파일의 Git 제외와 브라우저 공개 범위가 README에 정확히 설명된다.

### 6단계: 품질·정리·운영 문서

- `.DS_Store`의 기존 추적을 해제하고 `.env` 계열 실제 설정·`node_modules/`·`dist/`·테스트 결과·로그·임시 파일을 제외한다. 환경 예제와 재현 가능한 의존성 잠금 파일은 추적한다.
- 번호 생성은 유효한 1~45 정수 6개를 중복 없이 뽑도록 구성한다. 가중치 추출은 선택한 후보를 제거해 재시도 반복에 의존하지 않게 하고, 0·NaN·음수·누락 가중치를 처리한다.
- 입력 검증에 정수 여부·범위·중복·붙여넣기를 포함한다. 현재 `parseInt`로 소수를 잘라 받아들이는 동작을 수정한다.
- 통계 기준 회차·보너스 포함 여부를 표시한다. 빈도 기반 생성 설명은 과거 빈도에 따른 선택 방식임을 명확히 한다.
- 중복 HTML ID, 전역 변수 누출, 인라인 키 입력 이벤트를 정리한다. 모바일 번호 공·표·차트와 키보드 조작을 확인한다.
- 이미지 저장 기능·번호 1~5세트·통계 차트를 보존한다. 사용하는 라이브러리는 정확한 버전으로 고정한다.
- README에 로컬 실행·수동 갱신·설정·댓글 연결·Pages 설정·자동화 실패 복구를 기록하고 오래된 Java/LiveRe 설명을 교체한다.

검증 범위:

1. 공식 응답 변환, HTML/오류 응답, 누락·중복 회차, 번호·보너스 검증, 빈도 재계산, 실패 시 원본 보존, 재실행 멱등성을 Node 테스트로 검증한다.
2. 일반·가중치 번호 생성의 범위·중복·정렬·빈 데이터 처리를 검증한다. 랜덤 결과의 정확한 숫자를 고정해 테스트하지 않는다.
3. 홈·생성·통계·댓글·지도 주요 흐름을 데스크톱·모바일 화면에서 점검한다. 위치 거부·지도 키 누락·데이터 요청 실패도 포함한다.
4. 공식 사이트·giscus 같은 외부 서비스 검증은 단위 테스트와 분리한다. GitHub runner의 실제 네트워크 접근과 Pages 배포 후 데이터 기준 회차를 확인한다.

## 4. 예상 파일 구성

```text
data/                    # 당첨 기록, 파생 빈도, 갱신 메타데이터
js/                      # 공통 모듈과 화면별 코드
scripts/                 # Node 수집·검증·정적 배포 준비
tests/                   # 데이터·번호 생성 중심의 회귀 테스트
.github/workflows/       # 검사·자동 갱신·Pages 배포
.env.example             # 빈 값과 사용 설명만 제공
package.json             # dev / update-data / check-data / test / build
docs/IMPROVEMENT_PLAN.md
```

실제 파일명은 구현 과정에서 조정할 수 있다. 구현 단위는 수집·복구, 자동 배포, 화면·링크, 댓글, 지도, 정리 순으로 검토 가능하게 나눈다.

## 5. 외부 계정에서 필요한 설정과 남은 확인

- GitHub: Discussions 활성화, giscus 설치·카테고리 ID, Pages 배포 소스를 Actions로 설정, 자동 데이터 저장에 대한 브랜치 보호 호환 여부 확인.
- 카카오: 키 소유 앱, SDK 도메인 제한, 지도 활성화와 쿼터 확인. 기존 키 문자열은 이 문서에 복사하지 않는다.
- 데이터: 현재 확인한 JSON 경로는 공식 사이트가 사용하는 내부 조회 경로이며 안정성을 보장하는 공개 API 계약으로 간주하지 않는다. 변경에 대비해 어댑터와 오류 감지를 둔다.
- 네트워크: 현재 조사 환경에서는 신규 공식 JSON이 정상 응답했다. GitHub-hosted runner IP에서도 가능한지는 첫 수동 워크플로로 검증한다. 차단 시 우회하지 않고 마지막 정상 데이터를 유지하며 실행 환경을 다시 결정한다.
- 외부 설정을 완료하기 전에도 수집기·화면·테스트·안내 동선 구현은 진행할 수 있다. 실제 계정 설정은 구현 결과와 연결할 구체적인 항목이 준비된 뒤 적용한다.
